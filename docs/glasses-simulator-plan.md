# Plan: glasses simulator

## Goal and scope

Run the real vr-space window, capture, menus, camera, prediction and renderer without physical glasses. A person or AI can set and animate simulated head orientation and simulate connection changes through the command line; the AI can inspect structured state and capture screenshots without computer-use automation.

The simulator is separate code, not a separate rendering app. A small feature-gated integration in the main app is unavoidable: it must choose the pose source and expose simulator controls. Build the live-control interface in [cli-controls-plan.md](cli-controls-plan.md) first; reuse its socket, client, security, event-loop bridge, status and timeout/outcome-unknown rules rather than adding another service. No simulator code is needed to implement that plan.

## Starting and controlling it

- Add an opt-in Cargo feature and `--simulate-glasses` startup flag. Default builds and normal launches keep the real tracking path. A simulator-enabled build without the flag also uses real glasses. Simulation must never open or poll a real headset, even if one is connected.
- A separate simulator module owns simulated state and sample generation; `main.rs` chooses it instead of `spawn_tracking_thread`. Keep the integration points small and feature-gated. Label the simulated device clearly in the HUD and structured status so it cannot be mistaken for hardware.
- Use `--ignore-settings` and a normal window for the documented test launch, so testing does not overwrite the user's settings or require a glasses display. Don't automatically enable fullscreen. Real ScreenCaptureKit capture, the Mac display and Screen Recording permission are still required when testing captured content.
- Extend the existing `control` interface with simulator-only commands. For example (names are illustrative):

  ```sh
  vr-space control simulate pose --roll 0 --pitch 0 --yaw 30
  vr-space control simulate move --roll 0 --pitch 0 --yaw -30 --duration-ms 1000
  vr-space control simulate disconnect
  vr-space control simulate connect
  vr-space control simulate status --json
  ```

  Angles are **degrees in the existing fusion's FRD roll/pitch/yaw convention**; document axis signs and conversion to the app's existing radians. Test actual rendered directions using `head_rotation_from_pose`, rather than inventing a different camera convention. `pose` sets an absolute pose immediately; `move` moves from the current pose to an absolute target over the requested duration. Define and document interpolation, bounds, angle wrapping, and replacement of an in-progress move; reject non-finite, out-of-range or otherwise invalid inputs. Start connected at neutral pose (roll/pitch/yaw all zero). Pose and move commands fail clearly while disconnected; status remains available. Connect and disconnect are idempotent: repeating connect while already connected must not reset the pose, calibration or connection generation. Disconnect cancels motion; a real disconnected-to-connected transition starts a fresh session at neutral pose.
- This CLI also serves manual use; no new mouse/keyboard control scheme is needed initially. Simulator commands return an error when the running app is not in simulator mode. Ordinary app commands, including recenter, continue to use the live-control interface.
- Status reports simulator mode, connected state, current and target pose, motion state, sample timestamp and connection generation. Assign an app-lifetime monotonic revision to each accepted state-changing simulator command and return it in the acknowledgement. Report the active revision and motion completion/cancellation so scripts can distinguish their move from a replacement or reconnect without keeping an unbounded command history. A successful move request means accepted by the simulator, not completed; scripts wait for status to report completion. A timeout or lost reply is not cancellation and must not trigger an automatic retry: resending a move can restart its duration. Inspect status before deciding what to do next. Provide a submitted revision and frame counter so scripts can wait until a frame using their command's final pose sample has been submitted. Correlate that marker with the coherent pose sample actually used for the frame, not a separately read latest-command counter; a replacement or disconnect must not falsely complete an older move. Prediction may still offset the rendered orientation after measured motion ends; disable it explicitly for exact final-pose screenshot checks. Define it honestly: GPU submission is not proof of presentation; screenshot verification must account for the display and capture pipeline and cannot treat the marker alone as proof.

## Implementation

1. **Pose publication:** Publish simulated FRD samples through the same `PoseAtomic` path used by real tracking, using `now_ns_from_start()` for timestamps. Add the smallest shared session-publication helper needed to update the connection generation and connected/disconnected state exactly as `track_session` does. On reconnect increment the generation even if a render misses the disconnected interval; let the existing app logic reset recentering and prediction. The simulator thread is the sole writer of simulated pose and connection/session fields; the event loop only forwards commands. Publish a disconnected sample with zero angles, `has_device = false` and a fresh timestamp, matching the real failure path; publish the neutral connected sample for the new generation on reconnect. Ordinary app commands must never write simulated samples. A simulated disconnect does not test USB or the driver's reconnect logic.
2. **Motion:** A dedicated simulator thread publishes at a modest fixed cadence with fresh monotonic timestamps, including while stationary, and evaluates moves from monotonic elapsed time rather than accumulated sleep intervals. Keep simulated commands and state bounded and validate at the control boundary and against simulator-owned connection state. The event loop forwards requests without waiting; the simulator thread reports acceptance/errors and coherent status snapshots back through an event, then the event loop sends the CLI reply. Queue-full or rejected requests return errors, not success. A pose acknowledgement means its sample has been published; a move acknowledgement means the worker has accepted its start pose, target and duration, not that motion is complete. Avoid locks, allocations or blocking in the render/pose-read hot path. Sequence identical requests reproducibly in orientation and final state; OS scheduling, actual frame times and screenshot pixels are not guaranteed deterministic. Tests of interpolation should use an injected time, not sleep-based timing.
3. **Integration and safety:** Gate simulator-only CLI arguments, commands and module behind the feature. Keep regular tracking and calibration unchanged when simulation is off. Reject `--calibrate-gyro` with simulation rather than implying synthetic orientation samples exercised real gyro calibration. Reuse the existing control socket's single-owner rule. Unlike an ordinary second GUI instance, a simulation launch must fail clearly if it cannot acquire ownership and start its CLI listener; do this before starting simulated tracking or opening the simulation window. Acquire the actual lifetime lock, not just a racy preflight connection check. If another app owns it, leave that app and its socket untouched and instruct the user to stop it first; never silently direct simulator commands to it. Cleanly stop the simulator thread on app exit. Never change the actual system display configuration or Screen Recording permission.
4. **Documentation:** Explain the simulator build and launch, manual and AI command examples, angle convention, completion/status semantics, screenshot workflow and limitations in `README.md`. Update `ROADMAP.md` and the hardware checklist only where appropriate. No change to the standard signed production bundle unless simulator support is explicitly requested in a separate build.

## Verification

- Unit tests: degrees/radians and orientation mapping; interpolation at start/middle/end and replacement; input rejection; stationary timestamps; neutral startup; idempotent connect/disconnect; disconnect/reconnect generation and motion cancellation; worker rejection and acknowledgement semantics; command-specific completion/submission markers during replacement and reconnect; rejection of simulator commands in a real-tracking session. Use controlled time and avoid requiring hardware.
- Integration test: launch the simulation build without glasses using `--ignore-settings`; use only the CLI to set poses, recenter, move, disconnect and reconnect. Verify status, calibration/predictor reset and completed movement. Replace an active move and disconnect/reconnect during one; confirm an older revision cannot be mistaken for completion of the new command, or vice versa. Exercise timeout/lost-reply handling without automatic retries. With a known captured display/window and a normal Mac display, capture rendered-window screenshots after the completion marker and check visible orientation, recentering, HUD and layout. Test a changing capture source as well as a static one. Handle missing Screen Recording permission as an explicit environmental prerequisite, not a false pass.
- Regression: default build and simulator-enabled build without the flag still use real tracking; no USB probe occurs in simulation. Verify normal menu/CLI controls work, simulator commands reject a normal app, and the documented `--ignore-settings` simulation launch doesn't modify saved settings. Test a simulator launch while a real or simulated app owns the control socket: startup must fail without opening an uncontrolled simulator or disturbing the existing owner. Run workspace build and tests through `scripts/cargo.sh`, both binaries' `--help`, plus the feature-enabled build and tests. Visual checks may use screenshots; no real-glasses behavior should be claimed without hardware testing.

## What it cannot prove

Synthetic fused orientation bypasses the physical IMU, fusion, USB, real gyro bias/calibration and driver failures. It cannot establish optical quality, comfort, motion-to-photon latency, or actual tracking accuracy. Keep occasional real-glasses checks for those behaviors.
